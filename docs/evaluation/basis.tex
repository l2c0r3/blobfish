Ziel dieser Evaluation ist die systematische Vergleichsanalyse verschiedener Konfigurationen der implementierten Schach-Engine hinsichtlich ihrer Spielstärke und ihrer rechnerischen Effizienz.
Jede Konfiguration besteht aus einer Kombination aus Suchalgorithmus und Bewertungsstrategie.

Die Untersuchung orientiert sich an folgenden Forschungsfragen:
\begin{itemize}
\item Welchen Einfluss haben unterschiedliche Bewertungsstrategien auf die Zugqualität?
\item Wie wirken sich algorithmische Optimierungen auf die Rechenzeit aus?
\item Wie beeinflusst die zu berechnende Zugtiefe die Rechenzeit?
\end{itemize}

Zur Beantwortung dieser Fragestellungen wird ein kontrolliertes experimentelles Setup mit quantitativen Metriken verwendet.

\section{Versuchsdesign}
Die Studie folgt einem kontrollierten faktoriellen Versuchsdesign, bei dem mehrere unabhängige Variablen systematisch variiert werden, während alle übrigen Bedingungen konstant gehalten werden.

\textbf{Unabhängige Variablen}
\begin{itemize}
\item Suchalgorithmus (Minimax-Varianten mit Optimierungen)
\item Bewertungsstrategie
\end{itemize}

\textbf{Abhängige Variablen}
\begin{itemize}
\item Zugqualität
\item Rechenzeit
\end{itemize}

\textbf{Kontrollierte Variablen}
\begin{itemize}
\item Hardwareumgebung
\item Testpositionen
\item Konfiguration der Referenz-Engine (Stockfish mit fester Suchtiefe)
\end{itemize}

Die Suchtiefe wird nicht als unabhängiges Bewertungskriterium betrachtet, da sie direkt von der verfügbaren Rechenzeit abhängt und zugleich die Zugqualität beeinflusst.
Stattdessen wird sie als erklärende Hilfsgrösse betrachtet.

\section{Benchmarking-Ansatz}
Die Evaluation der Zugqualität erfolgt als Benchmarking gegen ein Referenzsystem, wobei Stockfish als starker Vergleichsmassstab dient.
Alle Engine-Konfigurationen werden auf identischen Schachpositionen getestet.
Für jede Position wird der von der implementierten Engine gewählte Zug mit den besten Zügen der Referenz-Engine bei gleicher Suchtiefe verglichen.
Dieser Ansatz ermöglicht eine relative Bewertung der Zugqualität, ohne auf absolute Bewertungswerte angewiesen zu sein.

Die Evaluation der Rechenzeit hingegen erfolgt als Benchmarking gegen den Minimax-Algorithmus ohne jegliche Optimierungen.
Auch hierfür werden alle Engine-Konfigurationen auf identischen Schachpositionen und auch auf identischer Hardware getestet.
Es wird für jede Position und alle definierten Zugtiefen der beste Zug berechnet.
Die Messungen werden mehrmals durchgeführt und die Rechenzeiten werden festgehalten.
Dieses Vorgehen ermöglicht eine relative Bewertung der Rechenzeit im Hinblick auf die Zugtiefe - wobei Ausreisser aufgrund der mehrfachen Wiederholungen der Messungen nur einen geringen Einfluss auf das Ergebnis haben.

Alle Messungen wurden auf demselben Rechner mit den folgenden Spezifikationen durchgeführt:
\begin{itemize}
    \item Betriebssystem: Microsoft Windows 11 Pro
    \item CPU: AMD Ryzen 7 7800X3D, 4.20 GHz, 8 cores / 16 threads
    \item Mainboard: MSI B650M GAMING PLUS WIFI
    \item RAM: 64GB DDR5
    \item GPU: RTX 4080 Super
\end{itemize}

\section{Datenauswertung}
Die erhobenen Daten werden mittels vergleichender Analyse und robuster statistischer Verfahren ausgewertet.
Medianwerte dienen dem Vergleich der zentralen Tendenz.
\gls{glos:mad} quantifiziert die Stabilität und Streuung.

Für die Auswertung der Resultate wurde erstmals eine Nutzwertanalyse angedacht.
Da Abhängigkeiten zwischen den Variablen (insbesondere zwischen Rechenzeit, Suchtiefe und Zugqualität) zu Verzerrungen führen können, wurde diese Methode nicht eingesetzt.
Stattdessen werden die Zugqualität und die Rechenzeit separat evaluiert.
Die Interpretation erfolgt anhand von einer rangbasierten Bewertungsmethode (für Zugqualität) und direktem Metrikvergleich (für Rechenzeit).

\section{Stockfish}
Die Engine wird mit Stockfish verglichen. Nicht, weil davon ausgegangen wird, dass die entwickelte Engine mithalten kann,
sondern vielmehr, um daraus zu lernen und einen Referenzpunkt zu haben.

Die grundlegende Idee besteht darin, \gls{glos:JUnit}-Tests zu schreiben, welche mit Stockfish interagieren. Dafür muss
Stockfish von der Maschine aus erreichbar sein, auf welcher der \gls{glos:JUnit}-Test ausgeführt wird.

Hierfür wird \href{https://testcontainers.com/}{Testcontainers} verwendet. Damit ist es möglich, während der
Testausführung beliebige Docker-Container zu starten und diese nach Abschluss der Tests wieder zu stoppen.

Da Stockfish selbst weder ein Docker-Image noch ein Dockerfile veröffentlicht hat, wurde mithilfe von
(\cite{stockfishCompilingFromSource}) und (\cite{socatExamples}) ein eigenes Dockerfile erstellt. Daraus können wir
ein Image bauen und einen Container starten.

Um während der Tests mit Stockfish kommunizieren zu können, wird einen Client benötigt. Ein weit verbreitetes
Kommunikationsprotokoll, das von vielen Schach-Engines und auch von Stockfish verwendet wird, ist das
\href{https://backscattering.de/chess/uci/}{UCI-Protokoll}. Damit kann Stockfish beispielsweise eine Position übermittelt
und der nächste Zug berechnet werden. Die von Stockfish unterstützten UCI-Befehle sind
\href{https://official-stockfish.github.io/docs/stockfish-wiki/UCI-\&-Commands.html}{hier} aufgeführt.

Sämtliche Klassen und Dateien, die entwickelt wurden, um Stockfish während der Tests auszuführen, befinden sich unter
\textit{src/test/java/ch/hslu/cas/msed/blobfish/stockfish} sowie \textit{src/test/resources/stockfish}.

\section{JUnit-Extension}

Um möglichst einfach innerhalb einer Testmethode mit Stockfish beispielsweise Positionen berechnen zu können, wurde
eine \gls{glos:JUnit}-Extension entwickelt. Eine Extension ermöglicht beispielsweise über Callbacks, Code
vor oder nach einer Testklasse oder Testmethode auszuführen (\cite{junitCallbacks}). Ebenfalls kann über PostProcessing Objekte in Felder der
Testklasse injected werden (\cite{junitExtensionRegistration}).

So sehen beispielsweise die ersten Zeilen der Testklasse \texttt{QualityTest}, welche die entwickelte Extension verwendet:

\lstinputlisting[
    firstline=34,
    lastline=39,
    firstnumber=34,
    caption={QualityTest - Extension},
    label={lst:qualitTestHead}
]{../src/test/java/ch/hslu/cas/msed/blobfish/QualityTest.java}

Mittels der Annotation \texttt{@ExtendWith(StockfishExtension.class)} wird die eigene Extension geladen. Dies bewirkt,
dass bevor die erste Testmethode ausgeführt wird, kontrolliert wird, ob lokal ein Docker-Container von Stockfish bereits
gestartet ist. Falls dies nicht der Fall ist, wird ein neuer Container gestartet.
Als Nächstes wird die \texttt{StockFishService}-Klasse, eine Fassade, innerhalb der Extension initialisiert. Dieses Objekt
wird dann mittels PostProcessing in das Feld auf Zeile 6 injected.

Anschliessend werden die Testmethoden ausgeführt. Innerhalb der Testmethoden kann nun via der \texttt{stockFishService}
Variable mit Stockfish kommuniziert werden, und so beispielsweise Positionen berechnet werden.
Zwischen den Testmethoden übermittelt die Extension den Befehl
\href{https://official-stockfish.github.io/docs/stockfish-wiki/UCI-\&-Commands.html\#ucinewgame}{ucinewgame} an Stockfish,
um die Engine zurückzusetzen.

Nachdem alle Testmethoden ausgeführt sind und ein Docker-Container für die Testausführung gestartet wurde, stoppt
die Extension den Container.

\section{Evaluationen lokalisieren}
\label{sec:evalpotenzmenge}

In den nachfolgenden Tests werden immer wieder Evaluationen, sowie deren möglichen Kombinationen, miteinander verglichen.
Die Kombinationen von den Evaluationen sind interessant, da so potenziell eine noch bessere Evaluation der Position
erreicht werden kann.


\texttt{EvaluationUtil} enthält eine Methode, welche alle möglichen Evaluationmöglichkeiten zurückgibt. \\
Dafür wurde \href{https://github.com/classgraph/classgraph}{classgraph} verwendet. Diese Java-Bibliothek ermöglicht es
unter anderem packages zu scannen. In unserem Fall wird es dafür genutzt, um alle Klassen herauszufinden, welche
das Interface \texttt{EvalStrategy} implementieren. Anschliessend wird jeweils ein Objekt davon initialisiert.

Somit wird noch eine Funktion benötigt, die eine Liste von Kombinationen von unseren Evaluationsobjekten zurückgibt.
Genauer genommen wird die \href{https://de.wikipedia.org/wiki/Potenzmenge}{Potenzmenge} als Basis benötigt.
Die Potenzmenge enthält nämlich alle Teilmengen einer Menge - also alle Kombinationen in aller möglichen Grössen, sowie
die einzelnen Evaluationsklassen (\cite{potenzmenge}):

So ist die Potenzmenge von $\{\texttt{a}, \texttt{b}, \texttt{c}\}$ folgende:

\begin{itemize}[noitemsep,topsep=0pt]
    \item $\emptyset$
    \item $\{\texttt{a}\}$
    \item $\{\texttt{a}, \texttt{b}\}$
    \item $\{\texttt{a}, \texttt{b}, \texttt{c}\}$
    \item $\{\texttt{a}, \texttt{c}\}$
    \item $\{\texttt{b}\}$
    \item $\{\texttt{b}, \texttt{c}\}$
    \item $\{\texttt{c}\}$
\end{itemize}

Die Funktionalität, die Potenzmenge einer Liste von Objekten zu ermitteln, wurde in die Klasse \texttt{PowerSetUtil} ausgelagert.
